Why not just use search?

The app already has vector (HNSW) + full-text (GIN) hybrid search. That stack is fuzzy & probabilistic — great at "what's roughly about X?", ranked. It does not give us:

1 · Tags as real data
The GENERAL prompt already emits tags[] — but it's buried in a JSONB blob; nothing parses, stores, shows, or filters it.
2 · Deterministic filtering
"Everything tagged vegetarian" = an exact set op with stable results, not a ranked guess that drops borderline matches.
3 · Entity extraction (new)
People / products / places / topics as discrete fields → facets like "all videos mentioning Cerave".
4 · Tag browsing / faceting
A finite, deduped vocabulary powers chip strips, "popular tags", combinable filters.
search finds  ·  tagging organizes
And it improves search too. Clean tags + entities are fed into the embedding and the full-text index, so even your existing semantic search gets sharper. Full mechanics in How filtering & search work below.

How filtering & search work

Two different jobs that work together. Filtering = "show me the exact set that has these tags." Search = "rank what's most relevant to my query." Tagging powers the first and sharpens the second.

Step 1 · what we store per transcript
"15-min vegan budget dinner" — by @PlantPlates
tags     = ['vegan', 'budget', 'quick', 'one-pot', 'tutorial']
entities = { products:['ninja creami'], people:[], places:[], topics:['meal prep','plant-based nutrition'] }

Tags are normalized (lowercased, deduped, capped). Entities are grouped by type.

tags attributes / labels
Short descriptors of what kind of thing it is — often adjectives or formats. Many per video, used as filter chips.
vegan · budget · quick · beginner · tutorial
topics subjects / themes
What the content is actually about — usually noun phrases / fields of interest, not formats.
meal prep · plant-based nutrition · intermittent fasting
tags vs topics — the honest answer: they overlap. Rule of thumb: a tag answers "how would I filter/shelve this?" (adjective-ish, reusable across many videos); a topic answers "what subject does it cover?" (noun phrase, the theme). To avoid double-listing the same word in both, the prompt will be instructed to treat topics as the meaningful subjects/entities a search query might name, and tags as the short reusable filter labels. If this split feels redundant, a clean alternative is to drop topics and keep only tags + the concrete entities (people/products/places) — fewer overlapping buckets. Want that?
Step 2 · filtering = exact set match (deterministic)
The flow
tap chip “vegan” → GET /transcript?tags=vegan → WHERE bt.tags && ARRAY['vegan'] → GIN index hit → exact set back

No ranking, no guessing. A transcript either has the tag or it doesn't. Same input → same result, every time. Fast because the GIN index is built for exactly this.

ANY vs ALL — in plain words
ANY = OR = broader
Filter vegan + quick → shows transcripts tagged vegan OR quick. (Postgres && overlap.)
ALL = AND = narrower
Filter vegan + quick → only transcripts tagged vegan AND quick. (Postgres @> contains.)

Default = ANY. When someone taps several tag chips they usually mean "show me anything in any of these buckets" (a wide net). ALL is for narrowing to the precise intersection. We default to ANY and offer an ALL toggle for power users. If you'd rather default to ALL, that's a one-line change — flag it.

Step 3 · entity filtering (the genuinely new bit)

Entities (people / products / places / topics) are extracted and shown in the detail view. If we later want exact entity filtering (Tier 3 below), it would look like:

“videos mentioning Ninja Creami” → entities -> 'products' @> '["ninja creami"]' → (needs Tier 3 column+index)
Your point (good one): if entities are only ever surfaced by search, do we even need the entity GIN index? — Correct, we don't. Three honest tiers:
• Tier 1 (recommended): entities live in structured_content only → they already flow into the embedding + full-text rank (see Step 4). No entities column, no GIN index. They're surfaced by search and shown in the detail view. Simplest.
• Tier 2: add an entities jsonb column for clean display/grouping, still no GIN index (no exact entity filtering).
• Tier 3: add column and GIN index only if/when we want deterministic "tap a product → exact filter".
This trims the original plan: tags get the dedicated column + GIN index (they're for exact filtering); entities can start at Tier 1 and ride search.
Step 4 · how search works today (with proof)

Verified from the real code: UserTranscriptRepositoryImpl.searchByEmbedding(...) and VideoService.buildEmbeddingInput(...). Quoted below.

A · What gets embedded (the search document)

When a transcript is saved, this text is what becomes the vector. Note the line already labels tags/entities — but it just dumps the raw structured_content blob:

Title: ...
Category: ...   Creator: ...
Description: ...
Structured metadata, tags, topics,
entities and key points: {…raw JSON blob…}
Transcript excerpt: ...(2500 chars)

Source: buildEmbeddingInput lines 645–651.

B · How a query is ranked

Three signals combined into one score (lower = better):

score =
  vector_distance              -- cosine, gate <0.70
  − LEAST(text_rank*0.25,0.35) -- full-text ts_rank_cd
  − exact_match_boost          -- 0.15 if ILIKE match

All three read the same concat: title, generated_title, description, structured_content::text, transcript (+ category.name for the ILIKE boost). Source: searchByEmbedding lines 124–185.

So today, tags/entities already reach search — but only as undifferentiated text inside structured_content::text. They influence both the vector and the full-text rank, but nothing weights or cleans them, and you can't filter on them. This is the proof behind "present but unusable".
Step 4b · future state — current vs after
SignalNowAfter this feature
Embedding (vector) tags/entities buried in raw structured_content blob add a clean, explicit Tags: vegan, budget, quick line → crisper, better-weighted vectors
Full-text rank matches messy JSON text (braces, keys) clean keyword tokens in the same concat → better keyword recall, fewer false hits
Exact filtering impossible (only fuzzy ILIKE) tags && / @> on the new GIN-indexed tags column
Filter + search combo — pre-narrow by tag, then rank within: "search only my vegan recipes"
Net effect: filtering gives exact control (new tags column + index); search gives relevance ranking (unchanged pipeline); and feeding clean tags into the embedding + full-text concat makes that existing ranking sharper. Minimal change to the search SQL — mostly we just feed it better input.

Backend changes

  • 1 Prompts — shared tags/entities block via one helper appended to all ~10 builders (no drift).
  • 2 Entity/domain model — add List<String> tags (setter-populated, like generatedTitle). Entities stay in structured_content (Tier 1).
  • 3 VideoService — parse → TagNormalizer (lowercase, trim, dedupe, strip #, cap 15/20) → persist.
  • 4 DTO + mapper — append tags, entities to TranscriptDtoWithAliases (end of record).
  • 5 Filter — repeatable tags param on / & /page; repo predicate via array overlap (any) / contains (all).
  • 6 Search — explicit Tags: field in embedding input + clean keywords in full-text index.
  • 7 Vocab endpoint — GET /transcript/tags → user's distinct tags + counts (drives the filter strip).

iOS (Scoop) changes

  • 1 Models — optional tags/entities on TranscriptResponse → domain → SwiftData (entities as entitiesJson).
  • 2 Mapper — carry tags/entities through API→domain→entity.
  • 3 Display — tag chips on card + detail (reuse SubcategoryPickerSheet chip language); entities grouped in detail.
  • 4 Filter UI — activeTagFilters chip strip populated from GET /transcript/tags (server vocab); taps drive server-side tag-filtered fetch.
Fully backward compatible: new JSON fields are additive & optional. Old clients ignore them; new client tolerates an old server.

Rollout & backfill

  1. Ship V28 + entity/prompt/normalization code.
  2. Deploy. New transcripts get tags immediately.
  3. Call POST /api/admin/reextract-and-reembed once in prod to backfill existing rows.

Idempotent & re-runnable; per-row failures logged. Default tags '{}' keeps un-backfilled rows valid (they just never match a tag filter).

Smaller alternative (phase 0)

If you want minimal scope: parse the GENERAL prompt's existing tags, expose + display + filter via JSONB — no V28, no new columns.

Drops: entity extraction, GIN index (slower at scale), cross-category contract, entity UI. Upgradable to Option B later.

Risks & edge cases

Malformed LLM JSON
Defensive parse (reuse cleanJsonResponse); on failure store []/null — never fail the pipeline.
Migration on populated table
Safe defaults + IF NOT EXISTS; no data rewrite. Columns empty until backfill.
Criteria has no array operator
Wrap &&/@> in a SQL function, or fall back to a native @Query like searchByEmbedding.
Tag explosion / casing
TagNormalizer caps 15 tags / 20 per entity group; server normalizes filter params so client casing is irrelevant.
